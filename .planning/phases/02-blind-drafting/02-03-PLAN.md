Brief sections, in this order, using these exact headings (the tests locate two of them):
1. `# Drafter brief`: one paragraph. Task: for each control in the catalog extract below, propose either a not-applicable rule or "no rule" for an archived repository snapshot target (an archived copy of a repository taken at one point in time). Use only the text in this brief; use no tools, files or outside information about any particular target; return a single JSON document and nothing else. Say nothing about who asked, any assessment, any target repository or any consumer of the result.
2. `## What each outcome means`: no rule resolves to APPLICABLE for every target whatever the facts, which is a real claim that the control applies to every archived repository snapshot, not a neutral default; a rule resolves NOT_APPLICABLE only when every field it names is known and every condition is met, APPLICABLE when every named field is known and not every condition is met, and APPLICABILITY_UNRESOLVED when any named field is UNKNOWN; UNKNOWN never yields NOT_APPLICABLE; absence of evidence is not not-applicable. Build this section from V2.RESOLUTION and V2.semantics()['statements'].
3. `## Rule shape`: combination ALL_CONDITIONS_MUST_MATCH; 1 to 4 conditions; each condition has field and state; states KNOWN_TRUE or KNOWN_FALSE only; each field at most once; usable fields production, internet_exposed, contains_customer_data, ai_enabled with their four definition sentences taken from V2.FIELD_DEFINITIONS; owner, tier, service_criticality and data_classification are not usable (use V2.semantics()['fields_not_usable_in_rules_statement']).
4. `## Drafting posture` (D-06 to D-10, directive form): lean to no rule; propose a rule only when the control name itself points at one of the four rule fields; never propose a control as switchable-off on a guess; use the fewest conditions that justify the rule, normally one, because each added field is one more that can be UNKNOWN; a control that would need an "or" is drafted as a narrower single condition list or as no rule; six entries are not REPOSITORY scoped, and where scope is the real reason a control might not apply and the four fields cannot say so, record a shape_limitation note; there is no third outcome, every entry is a rule or no rule; give every entry a confidence of HIGH, MEDIUM or LOW and an alternative_considered (the outcome rejected and why, or null).
5. `## Interpretation and rationale`: none of the catalog entries has a description (state this once); the seed rationale field in the entries is boilerplate and not a definition; reading the control name using general engineering knowledge is allowed, and that reading goes in the separate interpretation object with label DRAFTER_ASSUMPTION_NOT_AN_EMS_SOURCE as the drafter's assumption; each rationale is two to four sentences, ends each sentence with a period, avoids abbreviations containing periods, stands alone, names its own control's practice, uses no cross-references or shared reason codes between entries, and covers: why the outcome follows from the interpretation; for a rule, why the named field and state mark the control as not applying in terms of the approved field definition; for no rule, why none of the four fields gives a sound exemption.
6. `## Catalog extract`: one fenced json block holding a JSON list of exactly the 21 catalog entries for V2-catalog ids in MODULE.CONTROL_IDS, in that order, dumped verbatim from yaml.safe_load output (all eight keys per entry, no field added or removed, no other control).
7. `## Header to copy`: one fenced json block holding MODULE.expected_header() as JSON (indent 2). Instruct the drafter that the output document is that object copied verbatim, plus one added top-level key `proposals` holding the list of 21 proposals.
8. `## Output format`: the keys of a proposal (control_id, proposed_outcome with values PROPOSE_RULE or PROPOSE_NO_RULE, proposed_rule as the rule object or null, catalog_inputs copying control_name, scope, scope_owner, evidence_authority exactly from the entry (inheritance_allowed and classification_status may also be copied), interpretation {label, text}, rationale, confidence, alternative_considered null or {outcome, why}, shape_limitation null or {scope, note} where scope is the entry's scope); one proposal per entry of the catalog extract in the same order; no other keys; no authority field, no decision id; return bare JSON with no code fence and no commentary. Show the format as a skeleton with angle-bracket placeholders only (for example "<ID from the extract>"); the skeleton must not use any real control id and must not show a rule with real values chosen for any control.

The brief must not contain any of: the target repository name, its commit SHA, 'Hayes', '2026-10-01', 'EMS_NOT_APPLICABLE_RULE_ABSENT', 'DEMO3-W1-REQ-001' (the gated brief tests in tests/test_archive_assessment_rule_proposals.py check this once the file exists).
